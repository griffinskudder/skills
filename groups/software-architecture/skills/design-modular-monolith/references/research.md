# Architecture research

## Modular monolith as a starting point

- Martin Fowler argues for one deployable when the domain is still taking shape. Boundaries are easier to adjust inside one application, and the overhead of operating distributed services can slow early product feedback. His 2015 argument draws on practitioner reports. He calls the evidence sparse, cautions that many monoliths are hard to split, and notes that experienced teams with well-understood boundaries may reasonably start with coarse services. [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html)
- Shopify reported giving components public APIs and ownership of their data. It cited replacing its tax engine as a benefit of isolating dependencies. Its later Packwerk retrospective found that a package could pass static checks and still fail when run in isolation because of dependencies introduced through initialization and autoloading. Some domain groupings also needed smaller packages to capture the dependencies of actual execution paths. These reports describe the experience of a large Rails codebase. [Deconstructing the Monolith](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity) [A Packwerk Retrospective](https://shopify.engineering/a-packwerk-retrospective)
- Use one deployable as a starting assumption. Identify candidate modules from actual workflows, business rules, and data ownership. Keep module APIs small, verify dependency rules in code, and exercise representative workflows to catch implicit coupling. One database can host data for several modules when ownership and write paths remain clear. Revisit awkward boundaries before adding indirection to satisfy a check. [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) [A Packwerk Retrospective](https://shopify.engineering/a-packwerk-retrospective)

## Hexagonal architecture inside a module

- Alistair Cockburn's original report separates the application from external technology. Driving adapters translate inputs from a UI, batch job, or test into application calls. Driven adapters implement capabilities the application needs from infrastructure such as a database. Cockburn groups ports by purpose and leaves their number to design judgment. A consequence is that a caller can exercise application behavior without the deployed UI or database. [The Hexagonal (Ports & Adapters) Architecture](https://alistair.cockburn.us/hexagonal-architecture)
- Apply ports and adapters selectively where they separate meaningful policy from technology. Use ordinary functions or methods for use-case entry points when sufficient. Define an explicit outbound contract where the application needs to express behavior independently of an external implementation. Test policy through its entry point and verify real adapter behavior at the actual boundary when persistence or protocol semantics matter. Start with fewer abstractions in straightforward CRUD. [The Hexagonal (Ports & Adapters) Architecture](https://alistair.cockburn.us/hexagonal-architecture) [A Packwerk Retrospective](https://shopify.engineering/a-packwerk-retrospective)

## When to extract a service

- Extraction can pay off when one capability needs independent scaling, releases, or failure isolation. Dehghani recommends weighing the business value against the cost of disentangling the capability and keeping each increment small enough to redirect callers and retire the previous path. Fowler identifies provisioning, deployment and rollback, monitoring, and incident response as operational prerequisites. [How to Break a Monolith into Microservices](https://martinfowler.com/articles/break-monolith-into-microservices.html) [Microservice Prerequisites](https://martinfowler.com/bliki/MicroservicePrerequisites.html)
- For a data-heavy migration, Todkar describes first separating application behavior and data logically inside the monolith, then moving them in stages while preserving one authoritative write copy. DoorDash reported first routing its Drive Portal API through a facade, testing behavior parity, and shifting traffic in monitored batches. The DoorDash report covers one part of a larger migration. [How to Extract a Data-Rich Service from a Monolith](https://martinfowler.com/articles/extract-data-rich-service.html) [Minimizing Risk for API Extraction in a Major Migration Project](https://careersatdoordash.com/blog/safe-api-extraction-migration/)
- Compare an extraction with improvements inside the current deployment and name how success will be measured. Map callers, writes and transaction invariants before splitting. A defensible first increment has a clear owner, an independently operable capability, a traffic and data cutover plan, and a recovery path that accounts for writes after cutover. Service extraction is optional once the current architecture meets the requirement. [How to Break a Monolith into Microservices](https://martinfowler.com/articles/break-monolith-into-microservices.html) [How to Extract a Data-Rich Service from a Monolith](https://martinfowler.com/articles/extract-data-rich-service.html)
