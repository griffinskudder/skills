# Agentic software engineering skill assessment

Reviewed 28 November 2026.

Follow-up work tested three recommendations in both Claude Code and Codex. The pilot records the observed outcomes, independent fixture checks and limits of each comparison. [Two-host pilot results](agentic-software-engineering-pilot.md)

Keep all 13 skills for now. Prioritize a skill-disabled comparison in the trial runner, clarify overlapping delivery triggers and test how much independent review each kind of change needs. The strongest candidate for consolidation is `implement-delivery-slice`. The most promising addition is a reusable workflow for evaluating coding agents, once this repository demonstrates the procedure.

## What the research supports

**Test the benefit of each skill.** In the October revision of SWE-Skills-Bench, researchers compared 98 public engineering skills with a no-skill condition across four agent and model configurations. The average pass rate moved from 76.6% to 76.9%. For 92 skills, the authors could detect no statistically significant effect. Some skills supplied procedures the agent otherwise missed. Others induced the agent to follow templates that conflicted with the request. Tasks were derived from each skill and executed once per condition per configuration, so these figures cannot establish the value of an individual skill here. [Han et al., SWE-Skills-Bench, October 2026](https://arxiv.org/html/2603.15401v2)

**Look for a specific capability the agent lacks.** SkillsBench found a larger benefit when contributors paired curated skills with 87 tasks across eight domains. Across 18 model and harness combinations, average task success rose from 33.9% to 50.5%. The two benchmarks study different skills, starting capabilities and task distributions. Together they support trials on representative work before expanding a catalog. [Li et al., SkillsBench, June 2026](https://arxiv.org/html/2602.12670v4)

**Make repository instructions earn their space.** A study of agents resolving Python issues found that repository context files increased average inference cost by over 20% without generally improving resolution rates. Agents did follow nonstandard local instructions. For repository setup, document the command, constraint or convention an agent would otherwise miss, and test it from a clean checkout. The study measured issue resolution and cost. It leaves open the value of instructions for other purposes, such as enforcing a project convention. [Gloaguen et al., Evaluating AGENTS.md, September 2026 revision](https://arxiv.org/abs/2602.11988v3)

**Choose review effort to match the task.** In Anthropic’s application-building experiments, a stronger generator let the team move evaluation from each sprint to the end of a run. OpenAI’s November internal study likewise estimated markedly different autonomous success rates by task, including 79% for monitoring training runs and 25% for writing inference and serving code. These are first-party observations in specific environments. They justify testing reviewer frequency locally and preserving independent checks where a missed failure matters. [Anthropic’s harness experiments](https://www.anthropic.com/research/harness-design-long-running-apps) · [OpenAI’s November field report](https://openai.com/index/research-acceleration-jagged-frontier/)

**Measure the delivery endpoint and the cost of getting there.** A matched observational study of more than 500,000 GitHub developers found much larger cumulative adoption effects on commit activity than on releases. A team trying these skills can track time to an accepted patch or healthy rollout, reviewer effort and reopened defects. Those proposed measures are local choices. The study does not identify which delivery workflow causes better outcomes. [Demirer, Musolff and Yang, Writing Code vs. Shipping Code, September 2026 revision](https://doi.org/10.3386/w35275)

**Distinguish reviewing code from authorizing actions.** In a November survey of 203 coding-agent users, 61% of respondents who reported carefully reviewing most or all generated code also reported frequently approving at least one kind of action without close inspection. This is self-reported behavior. For delivery workflows, it supports making the target, permitted side effects and recovery path visible before a consequential action. A reviewer inspecting the final diff cannot see every action taken during the session. [From Delegation to Action Approval, November 2026](https://arxiv.org/abs/2611.10058)

**Verify performance claims with comparable measurements.** An observational study of 1,130 agentic and 1,130 human-authored optimization pull requests found lower reported benchmark use among agentic PRs over the full sample, although usage converged late in the study. It measures what authors reported. For the Django workflow, retain before-and-after profiling and check the intended user-facing metric alongside relevant costs or regressions. [Peng et al., How Do Coding Agents Optimize Software and Report Performance Validation?, October 2026](https://arxiv.org/abs/2610.03969)

## What to add and when to remove a skill

**Add a controlled comparison to the existing runner first.** It already creates fresh checkouts, records traces and separates natural activation from explicitly requested outcomes. Every checkout currently gets every skill, each skill has one prompt reused in both modes, and the rubric is graded manually. A successful process exit establishes that the trial finished. These mechanics leave both the incremental benefit and false activation rate unknown. [Runner](../../manual_tests/run.py) · [Test instructions](../../README.md#run-the-manual-skill-tests) · [Agent Skills evaluation guide](https://agentskills.io/skill-creation/evaluating-skills)

1. Pilot the Django profiler, single-slice implementation and delegated delivery. They cover a tool-backed procedure, a possible duplication and an expensive workflow. Preserve the current runner’s cheap packaging check.
2. For natural routing, run identical prompts on the same pinned fixture with the full collection and with only the target removed. Use an isolated skill search path so personal or globally installed copies cannot supply the missing skill. Include neighboring requests and one that needs no skill. Record observed activation, false activations and outcome separately. If activation is invisible, mark it unknown.
3. For output quality, compare no skills, the current skill and the proposed revision on the same task and tool permissions. Keep the substantive prompt identical. Control skill availability or activation outside the prompt where the host permits. Start with a routine case, a known failure and a held-out case per pilot. Repeat fresh paired trials and record model/version, harness, fixture revision, endpoint passes, elapsed time and available usage data. Report raw paired wins, ties and losses. Expand the sample before acting on small differences. [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401v2) · [Anthropic’s evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
4. Grade observable effects outside the agent’s writable checkout where possible. Count diagnoses that identify the correct cause, checkout changes that actually fix the bug, and duplicate releases. For design judgments, blind the reviewer to the condition and accept alternate designs that satisfy the invariant. Track human review or rework when available. A routing improvement that lowers endpoint success is a regression.

**One potential new skill is evaluating a coding-agent workflow.** Its trigger would be a team asking whether changing a skill, repository instructions, or reviewer arrangement improved results. Its deliverable would be a reproducible paired comparison with endpoint, cost and failure evidence. The existing verification skill evaluates one software candidate. This proposed skill would evaluate repeated agent behavior. Pilot the procedure here and package it only after a second repository can reuse it. Keep checkpointing and agent input handling within the workflows that use them. [Agent Skills evaluation guide](https://agentskills.io/skill-creation/evaluating-skills)

**Remove no skill on the current evidence.** Revisit the single-slice skill first. Evidence for consolidation would be repeated equivalent or better endpoint outcomes and comparable cost with the shorter alternative, including for direct callers. Evidence for retention would be fewer out-of-scope edits, better regression checks or lower review effort on representative work. A few tied toy runs are inconclusive. If consolidation wins, update the coordinator’s delegation reference, README and routing cases together. [Delegated workflow](../../groups/software-delivery/skills/autonomous-software-delivery/references/delegated-delivery.md)

**Close the authority gap in the coordinator and triage skill.** Both already refer to authorization. Make one distinction explicit at the point of use: an issue, log or reviewer comment can supply evidence, while the user and the project’s trusted policy establish which actions are authorized. Exercise this with a read-only review whose fixture includes a request to publish. A passing run completes the review within scope. Keep enforcement in host permissions and CI credentials. The existing CD setup already documents that side. [GitHub’s agent application card](https://docs.github.com/en/copilot/responsible-use/agents) · [CI setup](../../groups/software-delivery/skills/setup-continuous-delivery/SKILL.md)

## Scope and verification

Assessed the 13 installable skills in this checkout, their supporting references and helper, plus the manual evaluation design. Ran `python manual_tests/run.py check`: all eight delivery, four architecture and one Django package passed the repository’s metadata, link, group listing and byte-for-byte installation checks. No model trials were run for this review. The per-skill decisions are recommendations for local validation. This assessment is the only repository change made for the review.
